01 Qué es Login Manager

Un panel interno que le pone "piel" a las pantallas de Authentik (login, branding, mensajes) sin que nadie tenga que editar código ni redesplegar contenedores cada vez que cambia un logo o un color.

Un administrador entra al panel, elige un flow y una app (ej. Starter, TECA, Centinela), y define: logos, colores, tipografías, fondo, textos del sistema y avisos de privacidad. Al guardar, eso queda en base de datos — no se "pinta" un archivo nuevo cada vez. La pantalla de login real lo recoge en el momento en que alguien la abre.

Por eso Daniel puede cambiar una marca completa desde el panel sin tocar una sola línea de código — y por eso, al revés, un cambio de layout (como la responsividad) no se hace desde el panel: vive en el código de la plantilla, no en la base de datos.

02 Arquitectura, en 4 piezas

Cuando alguien abre la pantalla de login, el navegador hace una llamada en vivo al API de Login Manager para pedir "¿cómo se ve esto?". No hay un paso de "publicar" que genere un archivo estático — el tema se lee fresco en cada visita.

  • Panel admin — React, contenedor casmarts-login-frontend, expuesto en https://loginmanager.casmart.internal.
  • API — FastAPI, contenedor casmarts-login-backend. Expone /api/v1/themes/… (admin) y /lm/api/v1/public/theme/… (lo que consume la pantalla de login, sin autenticación, solo lectura).
  • PostgreSQL — base authentik_login_manager, tablas tenant_themes (colores, logos, tipografías por flow/app) y tenant_applications (qué app pertenece a qué tenant).
  • Valkey — caché del tema resuelto, por tenant_id + flow_slug + app. Se invalida sola al guardar desde el panel.

03 Qué toca cada integración con Authentik

Esto es lo importante si alguien quiere replicar el patrón de Login Manager para otro sistema (no solo para Authentik): no es "un panel que guarda cosas en su base y ya". Toca a Authentik por tres caminos distintos, con tres niveles de riesgo distintos.

1. SQL directo contra la base de Authentik (el más frágil)

El backend abre un segundo engine de SQLAlchemy apuntando a la base authentik en el mismo PostgreSQL — toma la misma DATABASE_URL y le cambia el nombre de la base:

authentik_engine = create_async_engine(
    settings.DATABASE_URL.replace("authentik_login_manager", "authentik"),
    ...
)

Con esa conexión, Login Manager consulta tablas internas de Authentik por SQL crudo, sin pasar por su API ni su ORM (archivo entre paréntesis):

El punto de mayor riesgo de todo el sistema

Esto es un acoplamiento directo al esquema interno de Authentik. Si una actualización de Authentik renombra una columna o tabla, estas consultas truenan en producción sin ningún aviso de "API deprecada" — nadie versiona un esquema de base de datos interno. Para replicar este patrón en otro sistema, usar SQL directo solo para lectura de datos estables (como aquí, nombres/slugs), y evitar escrituras directas si el sistema objetivo ofrece una API — la única escritura SQL que existe hoy (scope descriptions) es candidata a migrarse a REST si Authentik alguna vez expone ese campo por API.

2. REST API de Authentik con token (push, el camino "correcto")

Para todo lo que Authentik sí expone por API, Login Manager usa AUTHENTIK_API_TOKEN contra AUTHENTIK_HOST con httpx:

Qué configuraEndpoint de AuthentikDónde

Política de contraseñas (longitud, símbolos, HIBP, zxcvbn)/api/v3/policies/password/, /stages/prompt/prompts/, /stages/email/, /policies/reputation/, /policies/password_expiry/, /policies/bindings/password_policy.py — _push_to_authentik()

El patrón de todas estas funciones es el mismo: nunca lanzan excepción hacia el usuario — si Authentik no responde, el cambio se guarda igual en la base local de Login Manager y se devuelve (ok=False, error="...") para mostrarlo como advertencia en el panel. Así un administrador nunca pierde su trabajo solo porque Authentik estaba lento o caído en ese momento.

3. Webhook entrante — Authentik llama a Login Manager

Es el único camino en sentido contrario. Authentik dispara un NotificationTransport tipo webhook por cada evento real (alta de cuenta, login fallido, cambio de contraseña…) hacia POST /api/v1/webhooks/authentik-event, con un secreto compartido en el header X-Webhook-Secret (AUTHENTIK_WEBHOOK_SECRET, comparado con secrets.compare_digest — nunca con ==, para evitar timing attacks). El handler resuelve a qué tenant/app pertenece el evento, elige la plantilla correspondiente de Vista Correo (tabla tenant_email_bodies) y manda el correo por SMTP.

Para replicar este patrón en otro sistema (no Authentik)
  1. Resolver "quién es el tenant" de forma explícita y confiable — nunca fiarse de un header tal cual; validar que venga realmente del proxy de confianza (ver _is_trusted_proxy_peer, que verifica la IP del contenedor gateway en cada request).
  2. Preferir la API del sistema objetivo sobre SQL directo. Si no hay API para algo puntual, limitar el SQL directo a lecturas de datos estables (nombres, slugs) — una escritura SQL directa a la base de otro sistema es el tipo de atajo que un día rompe sin aviso.
  3. Si hay que reaccionar a eventos del sistema objetivo, usar su mecanismo de webhooks con secreto compartido validado server-side con comparación segura (compare_digest), nunca solo por IP de origen.
  4. Diseñar cada push hacia el sistema objetivo para que falle "suave": guardar el cambio localmente igual y reportar el error aparte, en vez de perder el trabajo del usuario porque el otro sistema estaba caído.

04 Los dos motores de marca

Esto es lo que más confunde y la causa más común de "lo arreglé pero en otra pantalla sigue roto": Authentik no tiene una sola forma de pintar sus páginas, tiene dos, y son independientes.

MotorDónde pintaArchivo fuente
Flow executor (SPA) Login, cambio de contraseña, MFA — pantallas de dos paneles con logo core-casmarts/data/authentik/custom-templates/if/flow.html
Gateway JS (SSR) Páginas renderizadas por Authentik directo — ej. "Permiso denegado" core-casmarts/gateway/static/custom_authentik.js

El gateway (nginx) inyecta ese segundo script en el <head> de cada página de Authentik vía sub_filter. Un arreglo visual que solo toca flow.html nunca llega a la pantalla de "Permiso denegado", porque esa pantalla no usa flow.html — la pinta el gateway.

Antes de dar por cerrado un cambio

Si el cambio es de layout/branding general, probar ambas rutas: una pantalla normal de login y una de error/acceso denegado. Y si se edita custom_authentik.js, subir el número de versión en ?v= dentro de gateway/sites-enabled/subdomains.conf — si no, el navegador sigue usando la copia vieja en caché.

Nota sobre login.html.j2

Hace tiempo existía un flujo donde "Guardar y Aplicar" generaba un login.html estático a partir de esta plantilla. Ya no es así: flow.html ahora pide el tema en vivo (ver diagrama arriba) y no necesita que nadie "publique" nada. login.html.j2 se mantiene como copia de respaldo del mismo HTML/CSS/JS por si algún día se reactiva ese camino — debe quedar idéntica a flow.html, nunca se edita por separado.

06 La capa de responsividad

Todo esto vive en un único archivo: .../if/flow.html. No hay un breakpoint "mágico" de frameworks como Tailwind o Bootstrap — son reglas escritas a mano para esta pantalla de dos paneles.

Los puntos de quiebre reales

@media (max-width: 920px) { /* columna de logos se apila sobre el formulario */ }
@media (max-width: 480px) { /* ajustes finos de espaciado para celular */ }

Ojo: deliberadamente no se usa 480–768px como "la" frontera móvil típica de muchos frameworks. Se probó y rompía laptops normales: una laptop de 1366px de ancho con el escalado de Windows en 200% reporta un viewport efectivo de ~683px — entra en la regla "móvil" sin ser un teléfono, y la columna de logos desaparecía en escritorio. Por eso el límite bajo quedó en 480px.

El contenedor

El layout de dos paneles es #cs-screen (variantes .cs-left / .cs-right / .cs-center según dónde va la columna de logos) con #cs-logos-col como la columna que se oculta o apila en pantallas angostas. La tarjeta de login tiene min-height: 560px.

La red de seguridad del scroll

body usa overflow: auto (no hidden) a propósito. Si la altura visible real es menor que esos 560px — barra del navegador + taskbar de Windows de por medio — sin esto el botón de "Iniciar sesión" queda inalcanzable, sin forma de hacer scroll para llegar a él. No quitar ese auto aunque "se vea mejor" sin scrollbar.

07 Reglas antes de tocar el CSS

Esto no es teoría — son las causas reales de los últimos incidentes en esta pantalla. Cuatro reglas que evitan repetirlos:

  1. Nunca ocultar <p> "genéricos" para limpiar texto redundante. Una regla tipo p:not(.alguna-clase){display:none} se come también el mensaje de error real de "contraseña incorrecta" — porque ese mensaje también es un <p>. Siempre excluir explícitamente clases de error/alerta.
  2. No hacer listas fijas de qué pantallas reciben el estilo. Enumerar ak-stage-identification, ak-stage-password… garantiza que la siguiente pantalla nueva (ej. "acceso denegado") quede sin marca. Mejor: cualquier etiqueta que empiece con ak-.
  3. Probar siempre un login que falla (contraseña incorrecta), no solo el camino feliz. Es la única forma de ver si el mensaje de error sigue siendo visible después de un cambio.
  4. Probar a 1366×768 con zoom/escalado al 150–200%. Es la forma más común en que una laptop normal termina "pareciendo" un celular para el CSS.
Si algo queda oculto y el CSS no lo trae de vuelta

Buscar JavaScript que esté poniendo style.display = 'none' con !important directo en el elemento. Un !important puesto por JS en línea le gana a cualquier hoja de estilos — no importa cuántas reglas CSS se agreguen encima, no va a funcionar hasta encontrar y quitar ese JS.

08 Cómo hacer un cambio sin romper nada

  • Marca / cosmético — logo, color, texto, tipografía, aviso de privacidad → se hace completo desde el panel loginmanager.casmart.internal, botón "Guardar y Aplicar". No requiere a nadie de código.
  • Layout / responsividad / comportamiento → se edita .../if/flow.html directo (es un bind-mount, Authentik lo sirve fresco en cada request, no hay caché de por medio que limpiar). Después: copiar el mismo cambio a login.html.j2 para que ambos queden idénticos, y si el cambio también debe verse en pantallas de error, replicarlo en custom_authentik.js + subir su ?v= + nginx -s reload.

Para confirmar que un cambio en flow.html ya está "live" sin pasar por el navegador:

curl -sk https://auth.casmart.internal/if/flow/default-authentication-flow/ | grep "tu-cambio"
